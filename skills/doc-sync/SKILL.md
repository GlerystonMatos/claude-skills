---
name: doc-sync
description: Atualiza a documentação-base (docs-kb) deste sistema a partir das mudanças no código desde a última geração e lista os arquivos que preciso enviar manualmente ao Google Drive. Use quando o usuário pedir para atualizar ou sincronizar a documentação.
---

Argumentos opcionais: "modulo <nome>" (só um módulo) ou "full" (regenerar tudo).

Ferramentas: `powershell -NoProfile -ExecutionPolicy Bypass -File .claude/skills/doc-sync/scripts/kb-tools.ps1 <acao>` (ações: `detectar`, `auditoria`, `check`, `para-enviar`, `readme`, `manifest`, `finalizar`). Leia `docs-kb/README.md` para a organização da pasta.

PASSOS:
1. Ler docs-kb/_manifest.json. Se não existir, parar e avisar que a documentação inicial ainda não foi gerada. O manifest registra a última execução (commit, data, histórico em `execucoes`) e o hash de cada arquivo de código já processado (`hashes`).
2. Detectar mudanças desde a última execução até o momento com `kb-tools.ps1 detectar`. Ele junta o histórico do git (`<commit da última execução>..HEAD`), os arquivos em stage, as alterações no worktree e os arquivos não rastreados, e descarta o que tem o mesmo hash registrado na última execução (já processado — inclusive mudanças não commitadas que já tinham sido documentadas). Ignora node_modules, build, dist, target, bin, obj, docs-kb, .claude e arquivos gerados. Resultado em `docs-kb/_mudancas.json`. Se avisar que o commit da última execução não existe mais no histórico, avisar e sugerir "full".
3. Mapear arquivos alterados para docs usando o campo "fontes" do front matter (o script já faz isso em `docsARegenerar`):
   - arquivo alterado com doc existente: regenerar o doc;
   - arquivo novo sem doc: identificar o módulo provável (`moduloProvavel`, via `docs-kb/_mapa-arquivos.csv`) e criar o doc necessário (módulo, tela, entidade ou processo); arquivo alterado sem doc: avaliar se precisa de doc;
   - arquivo removido: marcar os docs afetados como possivelmente obsoletos (`obsoleto: true` no front matter do par). Nunca apagar um doc sem minha confirmação.
4. Mostrar o plano em lista curta (a regenerar, a criar, obsoletos). Prosseguir sem esperar, exceto para exclusões. Se mais de 15 docs forem afetados, perguntar antes de prosseguir.
5. Regenerar apenas os docs afetados, lendo somente suas fontes e o diff. Manter os templates e as regras da geração inicial: PT-BR; marcar "Confirmado no código" ou "Inferido (verificar)"; citar fontes; nunca copiar segredos; nunca inventar. Preservar as seções que não mudaram. Atualizar o campo commit no front matter.
5a. AUDITORIA (sempre, em toda execução, mesmo sem mudanças detectadas): rodar `kb-tools.ps1 auditoria`. Ele regenera de forma determinística o catálogo completo das operações de auditoria a partir de `cargas/Fontes/KrAudit.pas` (constantes `ac*` + `InicializaAuditoria`) e `KrConst.pas` (`iTab*`), com as units que usam cada constante: `upload/{suporte,desenvolvimento}/processos/auditoria-catalogo-de-operacoes[-NNNN-NNNN][-dev].md` (índice + partes por faixa de 50 números). Só regrava arquivos cujo conteúdo mudou; partes que deixarem de existir são marcadas `obsoleto: true`. Nunca editar esses arquivos à mão. Conferir no resultado: "Add não interpretados" deve ser 0 (se não for, ajustar o parser no script) e, se surgir nome de cliente nas descrições, incluí-lo em `$clientesNoPublico` no script e rodar de novo.
   Além disso, se `KrAudit.pas`, `KrUtilAuditoria.pas`, `DgAud.pas/.dfm`, `RlDgAud.pas/.dfm`, `dgCliAud.pas/.dfm` ou as rotinas de auditoria de `KrUtil.pas` (`AudName`, `GetListaOperacao`, `MostraAuditoria`) mudarem, regenerar também os pares descritivos: `telas/seguranca-usuarios-configuracao--auditoria-consulta`, `processos/auditoria-gravacao-dos-registros`, `processos/auditoria-do-sistema` e `entidades/registro-de-auditoria` (mantendo todos os filtros, botões, regras, histórico por documento e pontos de atenção).
6. Validar com `kb-tools.ps1 check` e corrigir o que ele apontar.
7. Rodar `kb-tools.ps1 finalizar`, que, nesta ordem: gera docs-kb/_para-enviar.md com três listas por pasta do Drive (arquivos novos, alterados e obsoletos — para eu remover no Drive manualmente), com caminho relativo a docs-kb/upload/; regenera docs-kb/README.md (objetivo, organização e índice de todos os arquivos); e atualiza docs-kb/_manifest.json (commit atual, data, nova entrada no histórico de execuções, fontes e hash de cada doc e de cada arquivo de código processado). Mostrar as listas de _para-enviar.md também no relatório.
8. Relatório curto: docs regenerados/criados/obsoletos e pendências "Inferido (verificar)".

REGRAS: não fazer commit nem push; não enviar nada ao Drive; não incluir segredos; aplicar o .editorconfig (sem .editorconfig na raiz: UTF-8 sem BOM, CRLF, linha final).

ORGANIZAÇÃO E SIGILO: só vai para o Drive o que está em `docs-kb/upload/`; arquivos de controle (`_manifest.json`, `_para-enviar.md`, `_mudancas.json`, `_mapa*`, `README.md`) ficam na raiz de docs-kb, fora de upload. Todo doc existe em par com o mesmo caminho relativo — `upload/suporte/<pasta>/<base>.md` (público, funcional; `categoria_sugerida: Suporte`, `confidencialidade: interno`, `fontes` apontando para o seu `-dev`) e `upload/desenvolvimento/<pasta>/<base>-dev.md` (restrito, técnico; `categoria_sugerida: Desenvolvimento`, `confidencialidade: restrito-desenvolvimento`, `fontes` com os arquivos de código). Os arquivos de código mapeiam para o `-dev`; ao regenerar um `-dev`, regenerar também o seu par público. Código, arquitetura, estrutura do banco, leiautes, possíveis defeitos, riscos de segurança, permissões especiais, usuários/nomes internos e nomes de clientes ficam só no `-dev`. Públicos só linkam públicos. Nomes de arquivo claros sobre o conhecimento contido (entidades pelo conceito de negócio, sem código de tabela).
